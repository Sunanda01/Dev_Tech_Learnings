Levels -> Physical -> Datalink -> Network -> Transport -> Session -> PResentation -> Application

1. Application Layer >  				HTTP,HTTPs,SMTP,IMAP,FTP,POP3,SSH protocols.
   - softwares are the part of app layer.

2. Presentation Layer > Encoding, Encryption, Serialization, JSON all transformation mostly.

3. Session Layer > RPC/NETBIOS/Session Managament create a session between two apps to do certain tasks.
   - work like a checkpoint to resume a download in between of signal break.

   - also have concept of Data Units: TCP-segment and UDP-datagram

6. Data Link Layer > MAC Address/Ethernet, Data Units: Frames

TCP Seq Number
- Every byte sent over a TCP connection is numbered
- The Sequence Number field contains the position of the first byte of data
- Helps the receiver to reassemble data in the correct order
- Enables re-transmission of lost segments
- Prevents duplicate data from being accepted multiple times
- Initial sequence numbers are shared with each other during the TCP three-way handshake

ACK Num
 - Used to confirm successful receive of data, ack num contain next seq num
 - Retransmission happened based on this
 - receiver send ACK as(Seq num + byte = next seq num) send what i need next after search in me, ACK num means how much he have and next what need
 
Together, Seg and ACK Numbers
- Detect lost segments
- Detect duplioate segments
- Enable retransmission of missing data
- Guarantee ordered delivery of data

 vid 22 > MTU MSS PMTUD
  
Maximum Transmission Unit (MTU) -> 
- Largest IP Packet without fragmentation. 
- Includes IP Header + TCP/UDP Header + Payload. 
- Ethernet eader not part of it. 
- Different links can have different MTU. 
- Excedding MTU can cause fragmentations or packet drops.
MTU is there so we can avoid fragmentation, Keeping packets within the MTU avoids fragmentation, which can introduce additional headers, processing overhead, and packet-loss/re-transmission inefficiency.

Maximum Segment Size (MSS) -> 
- TCP Only
- Maximum TCP Payload in a single segment without TCP Header
- MSS = MTU - IP HEader - TCP HEader/
- Standard Ethernet MSS = 1460 bytes (No one remeber this shit)
- Advertised during TCP 3-Way handshake
- carried in TCP MSS option
- helps to avoid fragmentation
 * MSS helps to make segments based on the mss and total data size

Path Maximum Transmission Unit Discovery (PMTUD) -> 
- Each router have an MTU through which segments hops and go to the destination
- Mechanism to discover PMTU, prevent fragmentation
- Sender starts with larger packets and router dropped oversized packets & send ICMP " Fragmentation needed" then sender reduce packet size and try again -> this way continue until packet passes successfully

also during PMTU we set DF = 1  [means packet cant be fragment] so lower MTU router after receive a larger packet it will not fragment it , instead it drops and return ICMP (Internet Control Machine Protocol) "Fragmentation Needed"

SUMMARY:
- MTU: Maximum IP packet size on a link
- MSS: Maximum TCP payload in a segment
- PMTU: Smallest MTU along the path
- PMTUD: Process of discovering that PMTU

- Stop & Wait  -> send a packet and get next seq num as ack and then send next packet, this is ok when data is smaller but sending a 2GB data will cause issues and slow

- Cumulative ack : Instead we can send multiple segments at a time, then server send a single ack of next what it needs

Window size -> helps to maintain flow control, window size as the amount of data the receiver is currently willing to accept without sending another acknowledgment.
after get a receiver sends cumulative ACK and current window size. --- window updated event

 Vid 24 > TCP Congestion control

- Flow control: Prevents the sender from overwhelming the receiver.
- Congestion control: Prevents the sender from overwhelming the network. basically sender sends amount of data that router can handle.

sender window = min (congention window, recievers window)
How to know Congestion window > detects congestion window using try and error algorithm (Tcp Slow start, Assumption)     
There are congestion check algorithms and techniques as well.

Slow start: aggressively grow Congestion window (CWND)
Congestion avoidance: gracefully grow Congestion window

How TCP Detects Congestion?
1. Retransmission Timeout (RTO) 
Sender transmits a segment
Expected ACK does not arrive before the timeout expires
TCP assumes severe congestion or packet loss
Considered a strong indication of congestion

2. Triple Duplicate ACKs
Receiver repeatedly acknowledges the same missing packet
Sender receives 3 duplicate ACKs for the same sequence number
TCP assumes a packet was lost due to congestion

> Summary
TCP Congestion Control prevents the network from becoming overloaded
RWND (Window Size) protects the receiver while CWND protects the network
During Slow Start, CWND grows exponentially and increases by 1 with each ACK
Once SSTHRESH is reached, TCP enters Congestion Avoidance, where CWND grows linearly
TCP detects congestion using Timeouts, Triple Duplicate ACKs, or ECN
When congestion is detected, TCP reduces CWND and adjusts SSTHRESH to reduce network load

Video 39> QUIC protocol overview
- Developed by Google, later standardized by the IETF
- Transport layer protocol that runs over UDP
- Foundation of HTTP/3Provides reliable delivery like TCP
- Implements: Congestion Control, Flow Control, Packet Loss Recovery
- Integrates TLS 1.3 (no separate TLS layer) : without TLS no encryption, data send in readable format
TLS is implemented inside QUIC
- Implemented in user space, not inside the OS kernel
- Applications (Chrome, Firefox, Cloudflare, Nginx etc.) ship their own QUIC implementation
- Faster evolution compared to TCP because no OS update is required:
>>> 2 layers:
a. Kernel Space (OS) : This is where TCP/IP stack lives inside the Operating System.
b. User Space - green box: This is where your Apps like Chrome, Firefox run.
The problem with TCP:
- If you want to improve TCP, you have to update the OS of every single computer/phone in the world. That's very slow. Takes years.
** The smart trick of QUIC: They didn't touch TCP. They built QUIC in User Space.
QUIC just uses the existing UDP that is already in the OS. No OS change needed.
So, applications can bundle their own QUIC implementation. Chrome can ship a new, better QUIC with just a browser update.
- Result: Super fast evolution. No need to wait for Windows / Linux / Android OS update.

why UDP? Why not just: HTTP/3 -> QUIC + TLS 1.3 -> IP; Reason: Protocol Ossification
Internet devices (routers, NATs, firewalls) are made only for TCP/UDP. If we make a new protocol, they block it. So deploying new protocols became almost impossible. 
QUIC's fix: It hides inside UDP. 
Middleboxes see it as normal UDP and allow it.
Benefit: App can update QUIC itself, no need to depend on:OS vendors, Router vendors and Network upgrades

QUIC Handshake 
- Normal TCP needs 2 handshakes: 1 for TCP + 1 for TLS = 2-3 RTT before you can send data.
- QUIC merges both in 1 RTT:
	1. Client -> Server: QUIC Initial packet (contains TLS Client Hello + transport params)
	2. Server -> Client: QUIC Initial packet (contains TLS Server Hello + transport params)
	3. Client -> Server: Finished + 1st HTTP Request together
	So, QUIC + TLS handshake = 1 RTT only. After that, business data starts immediately.
Bonus: If client has talked before (0-RTT), it can send data in the very first packet itself. based on session-ticketID. can be used only with GET and HEAD req

Ouic Connection Migration:
- TCP identifies conn based on dest/src ip/port, if client's IP changes then TCP conn breaks 
- Quic introduces Connection IDs (CIDs): Conn identified using CID. If client's IP changes then also QUIC connection continues.

video 44> Mathematics behind diffie hellman
Diffie-Hellman (Whitfield Diffie and Martin Hellman)
- Key exchange protocolUses publicly known parameters: prime p and generator g
- Based on the Discrete Logarithm Problem
- ECDHE is the modern elliptic-curve variant widely used in TLS
- Diffie-Hellman is key exchange algo, not message encryption

Basic Diffie-Hellman example to get a symmetric key.
We want a shared secret, but we are on an untrusted network. We can only send public values.
1. Public parameters (everyone knows):
	Prime p = 23	
	Generator g = 5
2. Private secrets (never shared):
	Alice picks private a = 6
	Bob picks private b = 15
3. They calculate their Public Keys to exchange:
		Alice: A = g^a mod p = 5^6 mod 23 = 15625 mod 23 = 8
		Bob: B = g^b mod p = 5^15 mod 23 = 19
	They exchange A=8 and B=19 over the open network. An attacker sees 8 and 19, but can't get a or b because of the Discrete Logarithm Problem.
4. They calculate the SAME shared secret:
	Alice computes: Secret = B^a mod p = 19^6 mod 23 = 2
	Bob computes: Secret = A^b mod p = 8^15 mod 23 = 2
	Shared Secret = 2
This 2 is now the symmetric key. 
In real TLS, this number is much bigger (2048-bit) and then passed through a Key Derivation Function (KDF) to create the actual AES session key.
This is why DH is a key exchange algo, not encryption. It just lets both sides agree on the same symmetric key securely.

The router stores this mapping:

NAT TABLE

Private              Public              Destination
---------------------------------------------------------
10.0.0.4:3000   →   2.3.4.5:5555   →   8.8.8.8:53
10.0.0.1:3000   →   2.3.4.5:3000   →   8.8.8.8:53

Notice that both private devices can use the same public IP 2.3.4.5, because the router distinguishes their connections using different port numbers.

Response
8.8.8.8:53
     │
     ▼
2.3.4.5:5555
     │
     │ Router checks NAT table
     ▼
10.0.0.4:3000

So the key idea is:
PAT/NAPT = One public IP + different port numbers → multiple private devices can communicate with the Internet.

│     Identification                          │ Rsvd │  DF  │  MF  │    Fragment Offset     │
├───────────────────────────────┬──────────────────┴──────┴──────┴───────────────────────────┤

└─────────────────────────────────────────────────────────────────────────────────────────────┘

1. Version: Tells the receiver which version of IP is being used.
	IPv4 → 4
	IPv6 → 6
	
2. IHL — Internet Header Length
Tells the size of the IPv4 header.
IHL = 5 → minimum header size = 20 bytes
IPv4 can have optional fields.

3. DSCP — Differentiated Services Code Point
Used for traffic classification/prioritization. Routers can use DSCP to decide how traffic should be handled.

4. ECN — Explicit Congestion Notification
Used to indicate network congestion without necessarily dropping packets.
Instead of: Congestion → Drop packet
ECN can allow devices to communicate: "Network is becoming congested"
The sender can then reduce its sending rate.

5.Total Length: Specifies the total size of the IPv4 packet. Includes: Header + Data
Maximum IPv4 packet size: 65,535 bytes

6. Identification : Mainly related to fragmentation.
If a large IP packet needs to be broken into smaller pieces:
Original packet
       ↓
 ┌─────┬─────┬─────┐
 │ F1  │ F2  │ F3  │
 └─────┴─────┴─────┘
All fragments have the same Identification value, allowing the destination to know: "These fragments belong to the same original packet."

7. Flags: Controls fragmentation.
Important flags:
	> DF — Don't Fragment = 1, means: Don't fragment this packet.
		If the packet is too large for the next network and fragmentation isn't allowed, it can be dropped.
	> MF — More Fragments = 1, means:  more fragments are coming. The last fragment has: MF = 0
	
8. Fragment Offset: Tells the receiver where this fragment belongs in the original packet.
Example: Original: [A B C D E F G H]
After fragmentation: Fragment 1 → [A B C], Fragment 2 → [D E F], Fragment 3 → [G H]
The fragment offset helps the receiver put them back in the correct order.

9. TTL — Time To Live :  Prevents packets from circulating forever.
Example: TTL = 64
Router 1 → TTL = 63
Router 2 → TTL = 62
Router 3 → TTL = 61
...

Each router decreases TTL by 1.
When TTL reaches 0, the packet is discarded.
This protects the network from routing loops:
Router A → Router B
    ↑          ↓
    └──────────┘
Without TTL, a packet could potentially loop indefinitely.

10. Protocol: Tells IP which upper-layer protocol should receive the payload.
Common values: TCP   → 6, UDP   → 17, ICMP  → 1
For example:
IPv4 Packet
     │
     ├── Protocol = 6
     ↓
    TCP
So the receiver knows how to interpret the data.	

11. Header Checksum: Used to detect errors in the IPv4 header.
	Important: It checks the header, not the payload.
	Routers also recalculate it because fields such as TTL change at every hop.
Router
  ↓
TTL changes
  ↓
Header checksum recalculated

12. Source Address: The IP address of the sender.
13. Destination Address: The IP address of the intended receiver.
14. Data / Payload: Actual data being carried by the IP packet.
For example:
IPv4
 │
 └── Payload
      │
      └── TCP segment
           │
           └── Application data
Or:
IPv4
 │
 └── UDP segment
